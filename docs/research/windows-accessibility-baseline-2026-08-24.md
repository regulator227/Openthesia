# Windows-first accessibility baseline for practice visuals

Research date: 2026-08-24. This note answers [issue #15](https://github.com/regulator227/Openthesia/issues/15) using W3C, Microsoft, and Dear ImGui primary sources. It defines a product baseline; it is not a legal-compliance opinion or an accessibility certification.

## Recommendation and scope

Use the transferable Level A and AA requirements in WCAG 2.2 as the measurable baseline, interpreted for a native Windows application through W3C's [WCAG2ICT guidance](https://www.w3.org/TR/wcag2ict-22/), and add Windows platform conventions and settings. WCAG2ICT explicitly covers native software, but it is an informative Group Note rather than a normative standard and says non-web software can need requirements beyond WCAG. Openthesia therefore should describe the result as a **WCAG2ICT-informed Windows accessibility baseline**, not claim that the desktop app “conforms to WCAG 2.2 AA” without a separate audit.

The baseline should cover all five areas below. The first four and visible labels are feasible in the present stack. Programmatic labels for Narrator are also part of a defensible Windows baseline, but Dear ImGui does not supply them; that is a distinct architectural deliverable rather than a small styling change.

## 1. Scaling, text size, and reflow

Required behavior:

- Honor Windows' system text-size preference on startup and while the app is running. Windows exposes `UISettings.TextScaleFactor` from **1.0 to 2.25** and a `TextScaleFactorChanged` event for custom UI. Text, its containers, and associated controls must remain readable and operable at 225%; no label, value, command, or focus target may be clipped or lost. ([Microsoft accessible-text requirements](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/accessible-text-requirements), [Microsoft text-scaling guidance](https://learn.microsoft.com/en-us/windows/apps/develop/input/text-scaling))
- Treat **200% text enlargement without loss of content or functionality** as the WCAG-derived minimum (SC 1.4.4, Level AA). WCAG2ICT's software substitution says software should reach 200% itself or work with the platform's text-sizing capability to its extent; for Windows that makes the full 225% platform setting the appropriate product test. ([WCAG2ICT 1.4.4](https://www.w3.org/TR/wcag2ict-22/#resize-text), [WCAG 2.2 1.4.4](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html))
- Be Per-Monitor V2 DPI aware, react when a window changes monitors/DPI, and regenerate all DPI-dependent fonts, spacing, hit targets, and graphics. System-DPI awareness queries once and lets Windows bitmap-scale the app after a DPI change; Per-Monitor V2 receives DPI changes throughout the window tree and is the Windows model intended for monitor changes. Microsoft recommends declaring process DPI awareness in the manifest. ([DPI awareness contexts](https://learn.microsoft.com/en-us/windows/win32/hidpi/dpi-awareness-context), [`SetProcessDpiAwarenessContext`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setprocessdpiawarenesscontext))
- Apply reflow to navigation, settings, dialogs, textual status, and control bars. SC 1.4.10 (Level AA) uses a width equivalent to **320 CSS pixels** for vertically scrolling content and a height equivalent to **256 CSS pixels** for horizontally scrolling content, without two-dimensional scrolling or loss. WCAG2ICT maps this to window/dialog resize, content scaling, and screen-resolution changes and permits testing the nearest size the platform supports. ([WCAG2ICT 1.4.10](https://www.w3.org/TR/wcag2ict-22/#reflow), [WCAG 2.2 1.4.10](https://www.w3.org/WAI/WCAG22/Understanding/reflow))
- The piano keyboard and falling-note canvas can use the two-dimensional-layout exception where spatial position is essential to musical meaning. The exception does not extend to surrounding commands, labels, or settings. At high scale, a simplified text/current-target view is a sound alternative to forcing every detail of the piano roll to reflow.
- Use at least **24 by 24 device-independent pixels** for pointer targets, or satisfy the spacing/equivalent-control exceptions from SC 2.5.8 (Level AA). This is supplementary to, not a replacement for, keyboard access. ([WCAG 2.2 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum))

Chosen verification points should include display scaling at 100%, 150%, and 200%; Windows text size at 100% and 225%; a live move between monitors with different DPI; and the smallest supported window. Available display-scale values vary by hardware, so these are a practical test set rather than the limit of support.

## 2. Complete keyboard operation and visible focus

Required behavior:

- Every mouse action in the core flows is operable through the Windows device-independent keyboard interface without timed keystrokes (SC 2.1.1, Level A). Core flows include opening a song, choosing a mode, starting/pausing/stopping/restarting, seeking and changing speed, configuring hands, loops and bookmarks, changing settings, and returning to the prior screen. Path-dependent input can be excepted only when the underlying function truly depends on the path, not merely because the current implementation uses a drag. ([WCAG2ICT 2.1.1](https://www.w3.org/TR/wcag2ict-22/#keyboard), [WCAG 2.2 2.1.1](https://www.w3.org/WAI/WCAG22/Understanding/keyboard))
- Use the normal Windows model: Tab and Shift+Tab move among controls or control groups in a logical order; arrows move within a composite control and adjust sliders; Enter or Space invokes a command; Escape dismisses a popup or returns from a temporary mode. Focus must always be able to leave a component using standard keys (SC 2.1.2, Level A). ([Microsoft Windows keyboard guidance](https://learn.microsoft.com/en-us/windows/win32/uxguide/inter-accessibility), [Microsoft accessibility testing](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/accessibility-testing), [WCAG2ICT 2.1.2](https://www.w3.org/TR/wcag2ict-22/#no-keyboard-trap))
- Sequential focus preserves meaning and operability (SC 2.4.3, Level A), the focused item is not entirely hidden by a popup or fixed control bar (SC 2.4.11, Level AA), and a persistent visual focus indicator is shown for every keyboard-focusable item (SC 2.4.7, Level AA). ([WCAG 2.2 focus criteria](https://www.w3.org/TR/WCAG22/#navigable))
- For an objective house style, use a focus indicator at least as prominent as a **2-pixel perimeter** with **3:1** contrast between focused and unfocused pixels. That exact size is from SC 2.4.13 (Level AAA), while AA requires visible focus and at least 3:1 contrast for the necessary component/state cue under SC 1.4.11. The stronger metric removes ambiguity in a custom-rendered UI. ([WCAG 2.2 2.4.13](https://www.w3.org/WAI/WCAG22/Understanding/focus-appearance.html), [WCAG 2.2 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html))

Computer-keyboard piano input and UI navigation need explicit input scopes so a practice-note mapping cannot steal Tab, Escape, command shortcuts, or focused-control activation.

## 3. Color independence, contrast, and contrast themes

Required behavior:

- Never use hue as the only visual means of conveying hand, required note, correct/missed/early/late feedback, enabled state, or a requested action (SC 1.4.1, Level A). Pair color with stable text, icon shape, border/pattern, or position that has its own label. Examples are `L`/`R`, `Correct`/`Missed`, and `C#4`, not an instruction to “play the green note.” ([WCAG 2.2 1.4.1](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color))
- Maintain **4.5:1** contrast for normal text and **3:1** for large text (at least 18 pt regular or 14 pt bold/equivalent), SC 1.4.3 Level AA. Necessary control boundaries, states, focus cues, and graphical objects must be **3:1** against adjacent colors, SC 1.4.11 Level AA. These are threshold values and should not be rounded up. ([WCAG 2.2 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [WCAG 2.2 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html))
- Honor Windows contrast themes instead of treating a custom bright palette as “high contrast.” For a Win32/custom renderer, detect high contrast, take foreground/background colors from `GetSysColor`, omit background imagery, and remap multicolor graphics to the user-selected system colors. React to changes while running and test all four built-in Windows contrast themes. ([Microsoft high-contrast parameter](https://learn.microsoft.com/en-us/windows/win32/winauto/high-contrast-parameter), [Microsoft contrast-theme guidance](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/high-contrast-themes))
- Do not let velocity-controlled opacity make an essential note, label, or state fall below its contrast threshold. If opacity conveys velocity, show a textual numeric or categorical equivalent as well.

A grayscale pass is useful for finding color-only distinctions, but it does not replace ratio measurement or contrast-theme testing.

## 4. Reduced motion and visual effects

Required behavior:

- Respect the Windows client-area animation preference (`UISettings.AnimationsEnabled` or Win32 `SPI_GETCLIENTAREAANIMATION`) on startup and live changes. When animations are disabled, remove decorative transitions, easing/inertial panning, pulses, and similar nonessential motion. Respect `AdvancedEffectsEnabled` for transparency effects; in high contrast also avoid alpha blending, texture, and overlapped content. ([Microsoft composition tailoring](https://learn.microsoft.com/en-us/windows/uwp/composition/composition-tailoring), [Win32 client-area animation](https://learn.microsoft.com/en-us/windows/win32/winauto/client-area-animation), [Win32 high contrast](https://learn.microsoft.com/en-us/windows/win32/winauto/high-contrast-parameter))
- Expose an in-app `System / Reduce / Full` effects choice, defaulting to `System`, so a user can reduce effects without changing Windows globally. `Reduce` should disable note glow, transparency-dependent cues, smooth/inertial transitions, and nonessential animation while preserving the underlying music state.
- Provide keyboard-operable Pause and Stop for movement and auto-updating practice visuals. Automatically started motion lasting over five seconds alongside other content must be pausable, stoppable, or hideable unless essential (SC 2.2.2, Level A). Interaction-triggered nonessential motion must be disableable under SC 2.3.3; this is Level AAA, adopted here as product policy because Windows already exposes the preference. ([WCAG 2.2 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide), [WCAG 2.2 2.3.3](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions))
- Never flash more than **three times in any one-second period** unless a verified general/red flash threshold exemption applies (SC 2.3.1, Level A). The conservative baseline is simply to avoid faster flashes. ([WCAG 2.2 2.3.1](https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold))

Falling-note movement can be essential to that visualization, but the visualization is not the only possible practice interface. Reduced mode may keep user-started playback while offering a static current/next-note status or step/wait-for-notes view; it should not silently alter timing, scoring, or MIDI playback.

## 5. Alternative labels and Windows assistive technology

Required behavior:

- Provide a visible note-label mode that includes **pitch plus octave** (`C4`, `F#4`) rather than forcing users to choose pitch or octave separately. Add `L`/`R` hand markers and textual practice feedback such as `Current target`, `Correct`, `Missed`, and bar/beat or elapsed time. Give every icon-only command a concise text label available without mouse hover.
- Treat the piano roll as meaningful non-text content, not decoration. SC 1.1.1 (Level A) requires an equivalent text alternative; a non-text control needs a name that describes its purpose. A test/exercise that cannot be replaced by text still needs descriptive identification. WCAG2ICT says this applies directly to software. ([WCAG2ICT 1.1.1](https://www.w3.org/TR/wcag2ict-22/#non-text-content), [WCAG 2.2 1.1.1](https://www.w3.org/WAI/WCAG22/Understanding/non-text-content))
- Expose every interactive control and essential practice status through Microsoft UI Automation with a concise Name, correct control type/Role, current state and value, keyboard focus, applicable control pattern, bounding rectangle, and change events. SC 4.1.2 (Level A) applies directly to custom desktop controls through the platform accessibility API. ([WCAG2ICT 4.1.2](https://www.w3.org/TR/wcag2ict-22/#name-role-value), [Microsoft UI Automation specification](https://learn.microsoft.com/en-us/windows/win32/winauto/ui-automation-specification))
- Use a polite UIA live region for important, discrete practice updates when enabled; do not flood speech with every rendered frame. Microsoft identifies LiveSetting as the UIA mechanism for announcing important changed status/error text. ([Microsoft UIA live-region guidance](https://learn.microsoft.com/en-us/accessibility-tools-docs/items/win32/text_livesetting))
- Mark decorative glow, shadows, and backgrounds as absent from the accessibility tree. Visible text and tooltips help sighted users, but they are not a screen-reader alternative unless a UIA provider exposes them.

## Dear ImGui feasibility and current Openthesia implications

Dear ImGui can support a substantial visual/keyboard baseline, but it does not supply a complete accessibility framework:

- Openthesia currently pins ImGui.NET 1.90.1.1 (`Openthesia/Openthesia.csproj`). Dear ImGui 1.90.1 has full keyboard navigation behind `ImGuiConfigFlags_NavEnableKeyboard`; the current controller feeds key events but never enables that flag. Enabling it is necessary but not sufficient: piano and practice primitives drawn directly with `ImDrawList` are not automatically keyboard items, and application shortcuts/input scopes still need design. ([Dear ImGui 1.90.1 controls guide](https://raw.githubusercontent.com/ocornut/imgui/v1.90.1/imgui.cpp), [Dear ImGui 1.90.1 config flags](https://github.com/ocornut/imgui/blob/v1.90.1/imgui.h#L1335-L1348))
- In 1.90.1, correct scaling requires reloading fonts, rebuilding the font atlas, and calling `ImGuiStyle.ScaleAllSizes`; the latter is lossy and should be applied to a fresh base style when the scale changes. Openthesia currently reads DPI once, caps the font scale at 2.0, scales fonts but not the full style, and forces a `1280 x 720` minimum multiplied by that factor (`Openthesia/Core/ImGuiController.cs:78-105`; `Openthesia/Program.cs:21-48`). That cannot meet the Windows text-scale, reflow, or per-monitor requirements without restructuring. ([Dear ImGui 1.90.1 scaling source](https://github.com/ocornut/imgui/blob/v1.90.1/imgui.cpp#L1156-L1184))
- Dear ImGui's official project description says accessibility features are not supported, and its maintainer states that it is not accessible to most screen readers and that the library's design makes proper support difficult. Microsoft requires a custom UI Automation provider for custom controls. A UIA tree/bridge—or migration of user-facing controls to a Windows framework with built-in UIA—is therefore required before Openthesia can claim Narrator or screen-reader support. ([Dear ImGui README](https://github.com/ocornut/imgui), [maintainer statement](https://github.com/ocornut/imgui/issues/7892), [Microsoft UIA provider overview](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-providersoverview))
- Current hard-coded themes, direct draw-list colors, optional velocity-as-opacity, note glow, icon-glyph buttons, and separate `NoteName`/`Octave` label choices are specific audit targets (`Openthesia/Settings/ThemeManager.cs`; `Openthesia/Core/ImGuiTheme.cs`; `Openthesia/Ui/ScreenCanvas.cs`; `Openthesia/Ui/PianoRenderer.cs`; `Openthesia/Enums/TextTypes.cs`).

## Acceptance gates and decision implications

The baseline is met only when these release checks pass:

- Scale: no lost content/function at 225% Windows text size; no stale/blurry or wrongly sized UI after a mixed-DPI monitor move; controls remain reachable in the smallest supported window.
- Keyboard: complete each core flow with pointer input unavailable; verify logical forward/reverse focus, composite arrow navigation, Enter/Space activation, Escape dismissal, visible/unobscured focus, and no traps.
- Color: measure all normal-theme text/control/graphic pairs, inspect in grayscale, and run every built-in Windows contrast theme. Every hand and practice state still has a non-color cue.
- Effects: toggle Windows animation, transparency, and contrast settings before launch and while running; reduced mode removes nonessential glow/motion/transparency, Pause/Stop remain available, and no visual flashes over three times per second.
- Labels/UIA: verify visible combined note labels and status text. Use Accessibility Insights/Inspect and Narrator to verify each control's name, role, value/state, focus, action, and essential status updates. Microsoft's test guidance recommends a complete keyboard/Narrator run with the monitor off for primary scenarios. ([Microsoft accessibility testing](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/accessibility-testing))

For sequencing, scaling, keyboard navigation, color independence, contrast, reduced effects, and visible alternative labels can be the first implementation slice. UI Automation should be tracked as an explicit architectural follow-up with its own acceptance tests. Until that bridge exists, release notes should say that visible/keyboard accessibility has improved but Narrator and screen-reader support is not yet available; visible labels alone do not justify a full accessibility claim.
